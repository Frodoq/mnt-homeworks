# Постмортем инцидента GitHub (21-22 октября 2018)

## Краткое описание

Длительный сбой, приведший к отображению устаревшей и непоследовательной информации (Issues, Pull Requests, комментарии) на GitHub.com. Данные в репозиториях Git не пострадали и оставались доступны.

## Влияние (Impact)

*   Пользователи видели недавно созданные Issues и комментарии, которые после перезагрузки страницы могли пропадать.
*   Отображалась устаревшая информация.
*   Были приостановлены некоторые внутренние процессы (веб-хуки, обработка событий).
*   Сервис был доступен, но данные на сайте были неконсистентными.

## Корневая причина (Root Cause)

Произошел сбой в инфраструктуре (сетевой раздел), который привел к рассогласованию данных между основными и резервными базами данных MySQL. Эти базы данных отвечали за метаданные (Issues, PR, комментарии).

## Решение и восстановление

1.  **Остановка систем:** Были приостановлены фоновые процессы для предотвращения порчи данных.
2.  **Приоритизация целостности:** Команда сосредоточилась на полном и корректном восстановлении данных, а не на скорости возврата в онлайн.
3.  **Восстановление из бэкапов:** Основным методом стала ручная синхронизация и восстановление данных из резервных копий.
4.  **Коммуникация:** Регулярные обновления публиковались на [статус-странице GitHub](https://www.githubstatus.com/).

## Уроки, выученные за время простоя (Lessons Learned)

1.  **Целостность данных превыше всего:** Было принято решение о длительном простое, чтобы гарантировать полное восстановление всех данных пользователей без потерь.
2.  **Тестирование отказоустойчивости:** Инцидент выявил уязвимости в архитектуре, которые требовали пересмотра.
3.  **Сложность восстановления:** Процедуры аварийного восстановления (Disaster Recovery) оказались более сложными и длительными, чем предполагалось.
4.  **Прозрачность:** Открытая коммуникация помогла пользователям понять проблему и быть в курсе процесса её решения.

## Предотвращение в будущем

*   Улучшение мониторинга сетевой инфраструктуры.
*   Пересмотр и регулярное тестирование процедур аварийного восстановления.
*   Внесение изменений в архитектуру баз данных для повышения отказоустойчивости.
